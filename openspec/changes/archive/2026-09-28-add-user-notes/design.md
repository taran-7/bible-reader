## Рішення

1. **Окрема GRDB-база, не UserDefaults.** Нотаток може бути багато, їх треба шукати й експортувати; SQLite з міграціями (`DatabaseMigrator`) дає місце для майбутніх полів. Останнє місце лежить у тій самій базі (таблиця `state`, `UserDatabase: KeyValueStore`), щоб UI-тести скидали весь стан користувача одним профілем.
2. **Ключ без перекладу.** `VerseKey(book, chapter, verse)`: KJV, Kralická й Огієнко нумеровані однаково, тож нотатка видна в усіх трьох. Синодальний має іншу нумерацію в Псалмах тощо; до таблиці відповідностей (6.13) нотатка до Пс 22:1 KJV показується на Пс 22:1 Синодального, а не на 21:2. Записано в tech debt.
3. **Усе в пам'яті, запис одразу.** `UserData` (@Observable) тримає масиви й словники, кожна зміна пишеться в базу. Помилка відкриття бази не блокує читання: `UserData(unavailable:)` працює в пам'яті.
4. **Пошук нотаток у пам'яті.** Нотаток мало (сотні), тож `contains` зі згортанням регістру й «ё» простіше й швидше за окремий FTS.
5. **Закладка на розділ** зберігається з `verse = 0`.
6. **Кольори підсвітки** напівпрозорі й однакові для всіх тем: текст теми лишається читабельним на світлих і темних фонах; виділення має пріоритет над підсвіткою.
7. **Профіль для UI-тестів.** У Debug `BIBLE_READER_PROFILE` задає підтеку в Application Support; кожен UI-тест бере новий UUID. У Release змінна ігнорується.
8. **Експорт** через `NSSavePanel`; пісочниці потрібен `ENABLE_USER_SELECTED_FILES = readwrite`.

## Рев'ю

- Помилки бази показуються банером; без бази — явне попередження, що зміни не збережуться.
- Спершу запис (одна транзакція на пачку), потім пам'ять.
- Лист нотатки лишається відкритим для свого вірша, навіть якщо під ним змінився розділ: ключ зафіксовано, даних не губить.
